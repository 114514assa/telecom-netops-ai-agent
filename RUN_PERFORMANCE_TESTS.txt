4. 端到端基准前，性能模式启动 FastAPI
--------------------------------------------------------

重要：
  不要使用 --reload
  不要先开多个 workers
  单 worker 作为本地 Agent 基线

PowerShell 窗口 A：

uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1

窗口 B 先检查：

Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/api/v1/system/model

health 应看到：
  status = ok
  workflow_ready = True

system/model 用于确认本次到底是：
  RAG 开/关
  LLM 开/关
  local_hf / openai
  fp16 / int8 / int4

6. 正式测试 A：完整 INT4 Agent
--------------------------------------------------------

推荐 .env：

REQUIRE_APPROVAL=true
RAG_ENABLED=true
LLM_ENABLED=true
LLM_BACKEND=local_hf
LOCAL_LLM_MODEL_ID=Qwen/Qwen2.5-0.5B-Instruct
LOCAL_LLM_QUANTIZATION=int4
LOCAL_LLM_MAX_NEW_TOKENS=96
LOCAL_LLM_TEMPERATURE=0.0

确保：
  Ollama 正常
  FAISS 索引已构建
  当前 RAG_KNOWLEDGE_DIR 与实际 knowledge 目录一致

重新启动 FastAPI 后：

python -m scripts.benchmark_agent_e2e `
  --label int4_full `
  --mode full `
  --concurrency 1 2 5 10 `
  --requests-per-level 20 `
  --repeats 3 `
  --warmup 2 `
  --timeout 180 `
  --pid 12345

如果暂时不传 PID，删掉：
  --pid 12345

full 模式含义：
  POST /incidents
      -> normalize
      -> inventory
      -> parse
      -> diagnose
      -> RAG
      -> compose
      -> awaiting_approval
  POST /resume
      -> approved
      -> finalize
      -> completed

因此这是完整 HITL 工作流时延，而不是单独模型生成时延。

12. 当前项目特别要注意的解释
--------------------------------------------------------

1) /api/v1/incidents 是 async FastAPI 路由，但内部调用 runtime.graph.invoke()
   是同步工作流执行。
   所以在单 worker + 本地模型下，并发提升未必带来吞吐线性增长。
   这不是测试脚本自动判定的 bug；要用实际 P95/P99/吞吐数据确认。

2) 不要为了让并发结果“更好看”先改成多 worker。
   local_hf 模型可能被每个 worker 各加载一份，显存与内存口径会变化，
   会破坏单实例基线的可比性。

3) nvidia-smi 采样的是整张 GPU。
   如果 Ollama embedding 和 local_hf 同时使用 GPU，
   gpu_mem_peak_mb 是服务环境整卡占用，不是单独 Qwen 模型占用。
   模型独立显存仍以 benchmark_quantization_v2 的结果为准。

4) 当前 REQUIRE_APPROVAL=true 时：
   “到审批点时延”和“完整归档时延”是两个不同指标。
   简历里不要混写。

5) HTTP 200 不等于业务成功。
   新脚本会进一步检查 workflow status：
   full 必须最终 completed。
